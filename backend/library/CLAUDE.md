# Backend Library — CLAUDE.md

Core library for Project Lenie providing document processing, LLM abstraction, embedding generation, and database persistence.

## Key Modules

### Feed review

The UI switches between single-item review (default) and a paginated list,
remembering the mode in the URL and local storage. Each visible item requests
suggestions again when the chosen model differs from its completed run.
Feed prompt v2 also proposes up to three new topics, sanitized and filtered
against the current catalog; only explicit acceptance creates a topic and membership.
Documents retain prompt v1 and their existing auto-apply path. `GET/PUT /feed_items/content_group_model` exposes the allowlisted
models and household default (`app_settings.content_group_suggestion_model`).
The built-in default is `openrouter/google/gemini-2.5-flash-lite` when OpenRouter
is enabled, otherwise the existing Bielik suggestion model. `POST
/feed_items/<id>/group-suggestions` accepts optional `model` and `force`;
completed runs are reused only for matching input and model, while active runs
are returned unchanged. GET suggestions includes `run.model`; `GET /feed_items/<id>/group-suggestions?model=` returns the active
run if there is one, else the newest run OF THAT MODEL, else the newest run (`feed_routes._pick_suggestion_run()`) — without it a panel set
to model A never saw its finished run once model B had a newer one, and waited for A forever. Document
suggestions and their auto-apply behavior continue to use the existing model.

**Prompt templates (UI-editable, versioned).** The topic-suggestion prompt lives in
the `prompt_templates` table (`prompt_templates.py`, migration `b4d8f2a6c915`), one
immutable row per `(task, variant, version)`, `variant` = `feed_item` / `document`;
the partial unique index allows one `is_active` row per pair. Texts are Jinja2
rendered in a `SandboxedEnvironment` with `StrictUndefined`; the closed variable
set is `catalog` (JSON), `material` and `schema` (empty when the model gets the
schema as `response_format`) — `validate()` renders both `schema` branches, so an
unknown variable or a syntax error is a 400 at save time, never a failed job. The
built-in `DEFAULTS` are the fallback when no row is active (fresh DB, tests) and
reproduce the pre-template prompt byte for byte (`test_prompt_templates.py`). Saving
inserts the NEXT version (`create_version(..., activate=True)`) — old wording is
never overwritten. A run records `prompt_template_id`, `prompt_version` (label such
as `feed_item-v3`, `feed_item-builtin` for the fallback; legacy runs keep
`content-groups-v1/v2`), tokens, latency and cost (`prompt_tokens`,
`completion_tokens`, `latency_ms`, `cost_amount/currency/status`, copied from
`response.usage`), and the input hash includes the label so a new wording is never
served from the old cache. REST (`prompt_template_routes.py`, user or service key):
`GET /prompt_templates?variant=` (versions, variables, built-in text), `POST
/prompt_templates` (`{variant, system_template?, user_template, note?, activate?}`),
`POST /prompt_templates/<id>/activate`, `POST /prompt_templates/preview` (renders a
draft against a real `feed_item_id` or sample text, no model call), `GET
/prompt_templates/comparison?variant=&days=` (completed runs grouped by model +
prompt version: runs, avg tokens/latency, cost per run and per accepted suggestion,
accepted/dismissed/pending, no_match runs). `POST /feed_items/<id>/group-suggestions`
accepts `template_id` to pin one version for that request. The cost per accepted
suggestion is only as good as the number of decisions made — compare samples of
similar size. `build_request()` assembles the exact request (prompt, system prompt and
whether it is sent, `response_format`) for the job and for `POST
/feed_items/<id>/group-suggestions/preview` (`{model?, template_id?}`, nothing queued or
sent). The model list for the `content_group_suggestion` task offers only models that
honour a JSON-schema `response_format` (`llm_model_registry._STRUCTURED_OUTPUT_TASKS`:
direct providers other than CloudFerro are dropped statically — OpenAI and Vertex
Gemini no longer appear —, OpenRouter models are dropped when the live catalog says no
structured outputs; unknown stays). Tests: `tests/unit/test_prompt_templates.py`,
`test_feed_prompt_preview.py`.

**Managing topics.** `PATCH /content_groups/<id>` renames (409 on a duplicate active name
or an archived topic), `DELETE` archives only an unused topic (409 + counts otherwise), and
`POST /content_groups/<id>/merge` (`{target_id}`, `content_group_service.merge_groups()`) is the
way to retire a topic in use: feed-item, document and reader-chapter memberships move to the
target (rows the target already has are dropped as duplicates), the source's suggestions are
re-pointed (a run that already suggested the target keeps that one and the source's pending
twin is dismissed) and the source is archived; topics only, both active. Response: `moved`
counts plus both groups. Tests: `tests/unit/test_content_group_merge.py`.

**Expiry of "Może kiedyś" items** (`feed_retention.py`, migration `c7a2e5d9b148`). A feed item
that is `saved_for_later` AND carries the priority group with `priority_rank` 100 (the same rule
the UI uses for its "Może kiedyś" button) expires `retention` months after `saved_at`: the
`feed_daily` job (04:00, before the long caption fetch) calls `expire_saved_items()`, which moves
it to `skipped` through `transition_item()` with the new review reason `expired` — so every move
is in `feed_review_decisions` and can be undone in the review history. Other saved items never
expire. The period is `content_groups.retention_months` (topics only, 1–120, NULL = default); an
item with several topics keeps the LONGEST one, archived topics do not count, the household default
is `app_settings` key `feed_maybe_later_retention_months` (built-in 6). REST: `PATCH
/content_groups/<id>` takes `retention_months`; `GET/PUT /feed_items/retention` (`{default_months}`,
null restores the built-in); `POST /feed_items/expire_saved` (`{"dry_run": true}` lists what is due,
without it runs the sweep now); `GET /feed_items` and the single-item responses add `expires_at` and
`retention_months` to saved "Może kiedyś" items. Tests: `tests/unit/test_feed_retention.py`.

**Topic hierarchy** (`content_groups.parent_id`, migration `d2f8b4a1c693`). A topic may have a parent
topic (3 levels at most, topics only; `validate_parent()` in `content_group_service.py` rejects a
cycle, an archived/missing parent, a priority group and a deeper tree with fixed messages the UI maps
to Polish). `POST/PATCH /content_groups` accept `parent_id`; `group_to_dict` returns it. Archiving a
topic re-points its children to its own parent; merging re-points the source's children to the target
(and lifts the target when it was a child of the source). The suggestion catalog items carry
`parent_id` only when set (a flat catalog keeps the exact old JSON and prompt hash); the prompt gets a
`catalog_tree` variable (`render_catalog_tree()`, indented "- name (id N)" lines; empty when nothing is
nested, and the guarded `{% if catalog_tree is defined and catalog_tree %}` block then renders nothing,
so old templates keep working) telling the model to pick the MOST SPECIFIC topic. The migration also
inserts prompt version 2 with that wording and activates it for each variant whose active template is
still the unedited v1. In code, `drop_ancestor_suggestions()` removes a suggested topic that is an
ancestor of another suggestion of the same answer OR of a topic the target already has — so
"Informatyka" is not proposed next to "Web development" whatever the model answers; the general topic
only collects what no more specific topic covers. Existing documents are not re-filed.
Tests: `tests/unit/test_topic_hierarchy.py`.

**Browse filters.** `GET /feed_items` also takes `media=video|article` (video = the feed source has
`type='youtube_channel'` OR the URL matches `_VIDEO_URL_PATTERN`, the same rule as the UI's `isVideo`) and
`maybe_later=only|exclude` (membership of an active priority group with `priority_rank` 100, the rule of
`feed_retention.is_maybe_later`); anything else is a 400. They feed the read-only "Przeglądaj" tab of
`/feed-review`. Tests: `tests/unit/test_feed_browse_filters.py`.

**Topic description** (`content_groups.description`, `String(300)`, topics only, migration `b5f2c8e1a7d3`). A one-line scope
of a topic that tells the model what belongs in it when the name alone is ambiguous ("OpSec i ochrona danych": identity theft,
leaked PESEL, scams as well as IT security). `POST/PATCH /content_groups` accept `description` (whitespace collapsed, blank or
`null` clears it, absent key = unchanged; 400 above 300 characters or on a priority group); `group_to_dict` returns it. The suggestion
catalog item carries `description` only when set (like `parent_id`), so it reaches the model inside the `KATALOG` JSON and a catalog
without descriptions keeps its old prompt hash; changing a description changes the hash, so completed runs are not reused. The
active prompt text does not mention the field — add a sentence such as "`description` opisuje zakres tematu" through a new
prompt-template version if a model ignores it. Tests: `tests/unit/test_topic_description.py`.

**Suggestion quality report** (`prompt_template_routes.build_quality()`, `GET /prompt_templates/quality?days=`, default 90, `0` = all).
For the latest completed feed-item run of every item: `missed_by_model` (the run suggested nothing although the reader later filed
the item under a topic by hand — with the `no_match` flag, the model's `new_topics` and `filed_under`), `new_topic_proposals` (names
grouped ignoring case and diacritics, with `count`, `avg_confidence` and example item ids) and `per_topic` (times suggested /
accepted / dismissed, never-suggested topics first). `execute_suggestion_job` keeps the proposals that `triage_new_topics()` discarded
as `raw_result.dropped_new_topics` (`name`, `confidence`, `reason`, `dropped_because` = `duplicate_of_catalog` / `duplicate_in_answer` /
`low_confidence` / `bad_confidence` / `invalid` / `over_limit`; at most 10, key absent when nothing was dropped), because `new_topics`
holds only the survivors — a model that answers with an existing topic's name as a "new" topic is a miss visible only there; the report
copies them into `missed_by_model[].dropped_new_topics`. A job that failed (HTTP 429 from the provider, a timeout) is retried by the worker on
the SAME run: the failed attempt leaves its message in `run.error`, and the attempt that finally succeeds clears the column and keeps the
message as `raw_result.retried_after` plus `raw_result.attempts`, so a run that needed retries is never mistaken for a clean one — the report
lists them as `retried_runs` and `/prompt_templates/comparison` counts them per model as `retried_runs`. The model call passes no
`analysis_job_id`: `llm_usage_logs.analysis_job_id` is a foreign key to `document_analysis_jobs`, and a `jobs.id` there made every usage insert
fail (swallowed by the recorder), so suggestion and tool-candidate calls had no usage row, no cost and no failed-call record. Read-only, user or service key; the `/lenie-topic-suggestion-quality` skill
reads it together with `/prompt_templates/comparison`. Tests: `tests/unit/test_prompt_quality.py`.

**Item comment.** `feed_items.review_note` (existing column, `PATCH /feed_items/<id>/note`, now
limited to 4000 characters) is the reader's comment for an LLM: what interested them and what to do
next. `target_text()` appends it to the material of a topic suggestion as "KOMENTARZ UŻYTKOWNIKA …"
(max 1000 characters, the item text is cut to make room). Tests: `tests/unit/test_feed_comment.py`.

**Discussion queue ("Do omówienia z LLM")** (`feed_items.llm_discussion_status` NULL/`open`/`done`,
`llm_discussion_at`, `llm_discussion_done_at`, `llm_discussion_result`, migration `e8c3a1f5b794`). A
SECOND axis, independent of the text decision (`status`: import / save / "Może kiedyś" / skip): an
item can be skipped, or expire out of "Może kiedyś", and still sit in the discussion queue.
`feed_monitor_service.set_llm_discussion(session, item_id, status, result=None)` flags (`open`, the
original timestamp is kept while it stays open), closes (`done` needs an open item, `result` is a link
or a note up to 1000 characters), reopens (clears the result) or unflags (`None`); it never touches
`status`, `saved_at`, `review_reason`, group memberships or `feed_review_decisions`. REST:
`PATCH /feed_items/<id>/discussion` (`{status: null|"open"|"done", result?}`; 400 invalid, 404 unknown
item, 409 closing an item that is not open), `GET /feed_items?discussion=open|done|any` (the `status`
filter stays optional, newest flag first), `GET /feed_items/discussion_summary` (`{open, done}`);
the item dict carries the four fields. The expiry sweep (`feed_retention.py`) leaves the flag alone.
A skill such as `/lenie-feed-review` can read the queue with `GET /feed_items?discussion=open` and
use `review_note` as the user's brief. Tests: `tests/unit/test_feed_discussion.py`.

**Seed document from a feed item** (`feed_seed_document.py`, no migration). `POST
/feed_items/<id>/seed_document` (user key) creates ONE `text` Document per feed item with the
synthetic URL `lenie://seed/feed-item/<id>` (same pattern as the recipe import's `file:///ksiazki/…`):
title "Zalążek: <title>", `text`/`text_md` built deterministically (no LLM) by `build_seed_markdown()` —
the user's comment (`review_note`), source URL/date/topics, the feed summary and a short "Do ustalenia"
checklist — and the item's active topics copied with `copy_feed_groups_to_document(…, "feed_import")`.
The feed item itself is not changed (status, `document_id`, discussion flag stay). Idempotent: a second
call answers 200 with `created: false` and the existing document id (201 on creation, 404 unknown
item). The item dict carries `seed_document_id`, resolved by ONE `seed_document_ids()` query per list
page. The seed is a starting point to continue in the normal `text` editor / with ChatGPT or Claude Code.
Tests: `tests/unit/test_feed_seed_document.py`.

`feed_monitor_service.py` keeps feed candidates separate from imported
documents. The `saved_for_later` state is a shared household queue: it stores
`saved_at` and `saved_by_user_id`, but never creates a `Document` or enters the
automatic import query. The REST API exposes `POST /feed_items/<id>/save-for-later`
and `POST /feed_items/<id>/restore`; deferred items can later use the existing
`/import`, `/skip`, or `/ignore` actions. Skips accept a structured `reason`
(`not_interested`, `duplicate`, `already_known`, `too_long`, `other`) stored in
`feed_items.review_reason` for future preference/AI filtering.

`feed_daily` runs check → `run_auto_import()` → `run_caption_fetch()`. The last step
fetches YouTube captions sequentially (`CAPTIONS_PER_RUN` documents per run, a
`CAPTIONS_DELAY_SECONDS` pause between them, newest first; one fetch takes ~45 s, so a
full run of 100 occupies the worker for over an hour) for `youtube` documents
in `URL_ADDED`/`TEMPORARY_ERROR` that came from an `auto_import` feed; it stops
after `CAPTIONS_MAX_CONSECUTIVE_FAILURES` failures in a row (typically an IP block)
and the rest waits for the next run. A fetch ending as `TEMPORARY_ERROR` (usually the rotating proxy's exit IP flagged
by Google) is retried once after `CAPTIONS_RETRY_DELAY_SECONDS` (60 s); the result reports `retried`/`recovered`.
Every attempt is logged in `external_service_events` (`youtube_captions`, operation `via_webshare_proxy` or `direct`,
`error_code` `GoogleSorryBlock` for the Google block) and shown on `/service-status` — the data for judging whether the
paid Webshare proxy is worth keeping. `run_check()` reports `new_items` and a `feeds`
list (id, name, items, new_items) shown on the Jobs page; per feed it also lists up to
`NEW_ENTRIES_LISTED` new non-ignored entries as `new_entries` (`feed_item_id`, `title`, `url`,
`status`) plus `new_entries_truncated`, which the Jobs page renders as links. A manual
`feed_check` / `feed_check_all` job (worker.py) runs `run_auto_import()` right after the check and
returns its result under `import`, so new items of `auto_import` feeds become documents without
waiting for `feed_daily`; caption fetching stays in `feed_daily`.

### Domain Model & Database

- **`db/models.py`** — `Document` SQLAlchemy ORM model: ~30 attributes covering URL, text content (raw/English/markdown), metadata, processing state. Methods: `get_by_id()`, `get_by_url()`, `populate_neighbors()`. `DocumentEmbedding` model for vector embeddings — optional `chunk_id` FK to `DocumentChunk`, set when the embedding was generated from a reviewed chunk (`generate_embeddings_from_run()`) rather than the fallback whole-document split.
- **Chunk analysis models** (backing `chunk_review_routes.py` / `document_analysis_service.py`):
  - `DocumentAnalysisRun` — one row per analysis pass over a document. `mode`: `transcript` (YouTube/movie STT — LLM rewrite + speaker labeling, chunk splitting by sentence) or `article` (webpage/link/text/book chapters — no rewrite step, markdown is already clean, so every chunk's `corrected_text` stays `None` by design; split by markdown headings). `status`: run review workflow, `created` → `in_review` → `reviewed` (`PATCH /analysis_run/<id>`), plus `superseded` — set automatically by `create_run()` on an unfinished sibling run of the same `document_id`+`scope` (abandoned attempt: double click, retry) when a new run for that scope lands; its still-open chunks are flipped to `skipped` and the run drops out of the "missing Obsidian notes" filter and all "latest run" queries (one-off backfill: [`imports/fix_duplicate_analysis_runs.py`](../imports/CLAUDE.md)). `scope`: human-readable analysed range (e.g. a book chapter title), `NULL` = whole document — a document can have several runs (e.g. one `split_only` run over a whole book plus one `article` run per chapter; different scopes never supersede each other).
  - `DocumentChunk` — one row per chunk of a run. `type`: `TEMAT` (on-topic) / `REKLAMA` (sponsored) / `SZUM` (extraction junk — portal nav, cookie banners; auto-approved, never sent to an LLM for note-writing). `status`: `pending` → `approved` (or `needs_reanalysis`/`split_requested`/`split`/`skipped`). `obsidian_note_paths` — array of vault-relative paths, populated by the `/lenie-obsidian-note` skill when a note is written from the chunk. `obsidian_note_not_needed` — reviewer flag "this TEMAT chunk is not worth a standalone note" (thin / uninteresting); the chunk stays in every other pipeline (still embedded when `approved`) but drops out of the "chunks still missing an Obsidian note" counter/filter. Set per-chunk via `PATCH /chunk/<id>` or in bulk via `POST /analysis_run/<id>/mark_notes_not_needed` (`{"value": bool}`, default true — flags only note-less chunks; `false` clears them). `document_repository._missing_obsidian_note_chunk_conditions()` also treats a **one-chunk document that already has a document-level `Document.obsidian_note_paths`** as covered (the document note *is* that chunk's note), computed at read time — no chunk-level write, works retroactively.
  - `DocumentTopicSection` — LLM-synthesized grouping of a run's chunks by topic (`chunk_positions` array of `DocumentChunk.position`). Drives the book/chapter drill-down view in `/chunks/:id` for runs above `SECTION_VIEW_THRESHOLD` chunks. Coverage is partial by design — LLM synthesis doesn't always assign every chunk to a section.
  - `DocumentRemovedLine` — training data for `article_cleaner.py`: lines a human removed from a chunk/document during review (`source`: `manual` or `szum_chunk`). Survives run/chunk deletion (`run_id`/`chunk_id` FKs are `SET NULL`) so aggregate queries (e.g. most-removed lines per portal) keep working after runs are re-created.
  - **Monologue speaker** — `DocumentAnalysisRun.speakers` with exactly one entry means the author talking alone (`role: "autor"`). `chunk_llm_analysis.monologue_speaker_from_byline()` builds it from `Document.byline` (first comma-separated entry); `create_run()` applies it automatically to transcript runs with no `>>` markers and no caller-supplied speakers, and `POST /analysis_run/<id>/set_monologue_speaker` (optional `name`, 400 without byline/name) does it on demand. `speakers_context()` frames a lone speaker as "Autor i jedyny mówca (monolog)" in the chunk prompts instead of "Uczestnicy rozmowy".
- **`db/engine.py`** — SQLAlchemy engine and session factories: `get_session()`, `get_scoped_session()`.
- **`document_repository.py`** — `DocumentRepository`: query layer using SQLAlchemy session. Requires `session` parameter. Methods: `get_list()` (paginated/filtered; each row also carries `has_text_md` and `has_readable_content` (= non-empty `text_md` OR at least one TEMAT chunk — the list enables "Czytaj"/"Chunki" on it, since the reader falls back to chunk topics for YouTube/movie documents without `text_md`), `chunks_missing/with_obsidian_notes`, `groups`, and `link_count`/`proposed_link_count` — confirmed/proposed `document_links` across both endpoints, batched via `_count_document_links()`), `get_similar()` (pgvector cosine search), `search_text()` (lexical `ILIKE` candidate search, diacritic-folded via `unaccent()`), `list_by_filters()` (filter-only listing, no text/embedding query — stage 6 session B; empty `filters` legally lists everything newest-first, `sort` maps `SearchSort` to `published_on`/`created_at` ordering, `RELEVANCE` falls back to `INGESTED_DESC`'s ordering since there's no query to score against), `get_next_to_correct()`, `get_count()`, `embedding_add()`, `embedding_delete()`. `get_similar()`, `search_text()` and `list_by_filters()` all accept an optional `filters: SearchFilters` (stage 6) applied via `search.sql_filters.build_document_filters()` — the same builder for all three, so lexical, vector and filter-only search share identical constraints (stage 11c removed the legacy single-value `project` kwarg — collection filtering goes through `filters.collection_name`, resolved against the `collections` lookup table).
- **`publisher_registry.py`** — deterministic stage-7A resolution of `publisher_name`/`publisher_domain`. `resolve_publisher()` returns `PublisherResolution.matches` with cardinality 0/1/N; `.publisher_id` is populated only for exactly one match. Names are exact after case/diacritic folding, domains after lowercase/`www.` normalization. Never use `.first()` to hide ambiguity. Publishers are publication portals and must never be confused with discovery `Source` or `InformationSource` provenance.
- **`search/name_resolution.py`** — stage-7B read-only resolution for author and discovery-source names. Returns every exact case/diacritic-insensitive canonical/alias match ordered by id; `.id` is only set for cardinality 1. Physical `DiscoverySource` means discovery channel in all new code. `InformationSource` is unrelated claim provenance and is never queried here.
- **`search_routes.py` / stage-8 `SearchService.search()`** — the new HTTP contract accepts natural or explicit requests. Query-less calls delegate without embedding; hybrid calls pass complete filters to lexical/vector paths, fetch enough candidates for offset pagination, apply requested published/ingested sorting, then slice. Invalid JSON/domain values return 400, unknown feedback returns 404, execution failures return a detail-free 503.
- **`search_service.py`** — `SearchService`: hybrid search orchestrator behind `POST /search`. `search()` combines `search_text()` (lexical) and `get_similar()` (semantic/pgvector) candidates, then `_merge_results()` scores and de-duplicates them using its own Python-side diacritic folding (`_normalise()`), which must stay behaviorally aligned with the SQL-side `unaccent()` folding in `search_text()`; filters are a `SearchFilters` applied identically to both repo calls in SQL, before `LIMIT`. A missing query is filter-only: `search_by_filters()` delegates to `list_by_filters()` and never calls `embedding.get_embedding()` (no wasted latency/cost for a query with no text to embed). Embedding failure degrades to lexical-only results; it raises RuntimeError only when there are no lexical hits either. The legacy `search_similar()` (`/website_similar`) path was removed in stage 12. Performance measurements and the ILIKE-vs-FTS / HNSW decisions live in [`docs/search-hybrid.md`](../../docs/search-hybrid.md).

**Database tables:** `public.documents` (31 columns), `public.document_embeddings` (vector similarity, optional `chunk_id` FK), `public.document_analysis_runs`, `public.document_chunks`, `public.document_topic_sections`, `public.document_removed_lines`, `public.control_questions`, `public.document_control_answers` — see [`database/CLAUDE.md`](../database/CLAUDE.md) for full column definitions.

### Obsidian vault reimport (Epic 42)

`obsidian_reimport_service.py` walks the vault (`OBSIDIAN_VAULT_PATH` config) and, through the normal `DocumentService.import_document()` pipeline, creates/updates read-only `Document` rows with `document_type="obsidian_note"` for every `.md` file under the sync folders from the `OBSIDIAN_SYNC_SUBFOLDERS` config key (not the whole vault; parsed/validated by `obsidian_sync_config.py`, shared by the full scan, the single-note resolver and the watcher) — **contrary to older docs elsewhere in this repo, the backend (NAS) DOES have runtime read access to the Obsidian vault for this path** (905 notes imported as of 2026-08). Synthetic identity/dedup key: `Document.url = f"obsidian://{relative_path}"` (mirrors the `gmail://...`/`file:///ksiazki/...` synthetic-URL conventions), resolvable with `Document.get_by_url()`. Change detection is content-hash based (`Document.obsidian_source_hash`, SHA-256 of the raw file — not mtime, since Obsidian Sync doesn't guarantee it survives cross-device sync): an unchanged file is skipped, a changed file updates the existing row in place (never duplicated) and re-embeds only that note. YAML front matter is stripped from the stored `text`/`text_md`; its `tags` field merges into `Document.tags`. Embeddings use the same whole-document split+embed fallback `documents_pipeline.py` uses for chunk-analysis-less documents — no LLM chunk classification, no human review gate, required for an unattended bulk import. After each create/update, a best-effort `content_group_suggestion_service.request_suggestions()` call enqueues async Bielik content-group (Tematy) classification (`backfill_obsidian_content_groups.py` is the one-off retroactive pass for notes imported before this hook existed).

`obsidian_vault_watcher.py` (Story 42.3) is an inotify-based watcher (`watchdog`) that enqueues a targeted single-note `obsidian_reimport` job (`job.parameters["relative_path"]`) the moment a file changes, instead of waiting for the next scheduled scan; a full-vault walk still runs once a day as a safety net.

This is the *reverse* direction from `Document.obsidian_note_paths`/`DocumentChunk.obsidian_note_paths` (see below) — those store a **link** from an already-imported article/chunk *to* a note written from it by the `/lenie-obsidian-note` skill; `obsidian_reimport_service.py` instead pulls existing vault notes *into* Lenie as their own searchable/embedded documents. A note's `obsidian_note_paths` entry and its reimported `Document.url` can be joined by normalizing the path (prepending the missing `02-wiedza/` prefix when absent) — `obsidian_note_paths` entries are not consistently vault-root-relative in older data.

### LLM Abstraction (`ai.py`)

Entry point: `ai_ask(query, model, temperature, max_token_count, top_p, *, system_prompt=None, response_format=None, operation="ai_ask", search_interpretation_log_id=None) → AiResponse`

Supported models:
- **OpenAI**: gpt-3.5-turbo, gpt-4, gpt-4o, gpt-4o-mini
- **AWS Bedrock**: amazon.titan-tg1-large, amazon.nova-micro, amazon.nova-pro
- **Google Vertex AI**: gemini-2.0-flash-lite-001
- **CloudFerro**: Bielik-11B-v2.3-Instruct, Bielik-11B-v3.0-Instruct (Polish)
- **ARK Labs**: `arklabs/<model>` (stateless/stateful GPU session variant)

Documents and prompts stay in their source language; there is no automatic translation helper or pipeline.

**Stage 3 of the search-rebuild plan (docs/search-rebuild-implementation-plan.md).** `system_prompt` is sent as a real system-role message — never string-concatenated with the user prompt — for providers that support it (`cloudferro`, `arklabs`); passing one for any other provider raises `ValueError`. `response_format` is forwarded to Sherlock only (`cloudferro`); other providers raise `ValueError`. **Verified live against CloudFerro Sherlock (2026-07-18):** `{"type": "json_schema", "json_schema": {...}}` is honored — the schema's required keys are imposed on the model's output — but `{"type": "json_object"}` is rejected with HTTP 400, so structured output requires a full JSON Schema, not the bare "give me JSON" mode. Provider-specific token field names (`prompt_tokens`/`completion_tokens` vs Bedrock's `input_tokens`/`output_tokens`) are unified internally before recording usage. After every call (success or exception) `ai_ask()` writes exactly one `llm_usage_logs` row via `library.llm_usage.recorder.record_llm_usage()` and attaches the resulting `UsageRecord` (tokens, latency, `usage_log_id`, `CostEstimate` with status) to `response.usage`; recorder failures (including `SystemExit` from `config_loader.require()` when DB config is absent) are logged and swallowed so a bad usage write never breaks the LLM call. `AiResponse` intentionally has **no** `cost_usd`/`cost`/`credits_used` attributes — cost lives only in `response.usage.cost`. Stage 3b removed the modules that used to probe for those dead attribute names (`timeline_events._response_usage()`/`_combine_costs()`, privately imported by `tones.py`/`time_periods.py`); all three now build their diagnostic reports via `library/llm_usage/report.py`.

**Stage 10 evaluation.** `library/search/evaluation.py` scores the partial expectations in `tests/fixtures/search_query_cases.json`: JSON-safe domain serialization, explicitly pinned fields only, and aggregate JSON validity, field accuracy, latency, tokens and same-currency cost. `imports/evaluate_search_queries.py` runs the real parser sequentially and, unless `--keep-audit` is passed, deletes only the exact audit/usage IDs produced by that run. The first real Bielik baseline is in `docs/search-rebuild-bielik-baseline.md`.

**Model allowlist, limits and prices.** `llm_model_registry.py` is the server-side allowlist of models a reviewer may pick (`/website_entities/<id>/describe/preview` and `/describe/arena`; `is_selectable()` is allowlist-only — no network, no database). `selectable_models()` adds each model's limits and prices without hard-coding them: an `openrouter/<id>` model reads the live public catalog (`api/openrouter/openrouter_catalog.py`, `GET https://openrouter.ai/api/v1/models`, no API key, no document text sent, so it works even with `OPENROUTER_ENABLED` off; 6 h in-process cache, stale catalog kept on a failed refresh, 120 s back-off after a failure, 5 s timeout), every other model its active `llm_pricing` row. Fields: `context_length`, `max_output_tokens`, `input_price_per_million` / `output_price_per_million` (Decimal strings, per 1M tokens), `currency`, `price_source` (`openrouter_api` / `llm_pricing` / null), `supports_structured_outputs`, `listed_by_provider` (false = an OpenRouter id the catalog no longer knows; null = catalog unreachable). Unknown stays `null` — never a guessed number. `model_details(model)` returns one entry (e.g. to size `max_token_count`). The recorder (`llm_usage/recorder.py`) prices an `openrouter` call from the catalog when `llm_pricing` has no row for it (usage row snapshots the rates, `pricing_version` stays null); a provider-reported cost still wins. Prices that no API publishes (CloudFerro Bielik, AssemblyAI in `transcript.py`) remain in `llm_pricing` / code. Tests: `tests/unit/test_openrouter_catalog.py`.

**Cost report and the OpenRouter balance.** `llm_cost_routes.py` serves `GET /llm_costs` (totals, `providers`, daily, operations, documents, analyses, and with `document_id` the call history) from `llm_usage_logs`; `providers` groups by `provider` (`openai`, `google-vertexai`, `aws-bedrock`, `cloudferro`, `arklabs`, `openrouter`) **and currency** with calls, tokens, cost, `unknown_calls` (no price in `llm_pricing`, so no amount — today every OpenAI and ARK Labs call, only the tokens are known) and `failed_calls`. An OpenRouter call is priced from the live catalog (`cost_status='estimated'`), not from the invoice. `GET /openrouter_balance` (`api/openrouter/openrouter_key.py`, cached 60 s) reads `GET /api/v1/key` with the same `OPENROUTER_API_KEY` and returns `balance` = `{status: ok|not_configured|unavailable, has_limit, limit_usd, remaining_usd, usage_usd, reset, low, exhausted}`; `remaining` exists only when the key has a spending limit set in the OpenRouter dashboard (`low` = 20 % or less of it left, `exhausted` = 0), otherwise only the usage is known. Whole-account credits (`GET /credits`) need a management key and are deliberately not used. Tests: `test_llm_cost_routes.py`, `test_openrouter_key.py`. Successful embeddings with known prompt usage are recorded with `completion_tokens=0`. OpenAI calls capture the provider token usage. OpenRouter calls store the provider-reported exact `usage.cost` (`cost_status='reported'`) and fall back to the catalog estimate when it is unavailable. `imports/backfill_llm_costs.py` prices old unknown rows once a price exists.

**Group entity descriptions.** `entity_description_batch.py` describes the undescribed organizations and persons of one chapter with a single quotation of the chapter: `candidates_for_chapter()` picks registry-resolved, non-country entities with an empty `organization_description` / `person_description` (one registry entry once, most mentioned first), `build_prompt()` addresses them by short ids (`o1`, `p2`) so the answer never depends on the model repeating a name, `response_schema()` forces one string-or-null value per id, `parse_answer()` tolerates fences, ignores invented keys and treats `null`/`BRAK`/non-strings as "chapter not enough", `describe_batch()` halves and retries an unparseable answer, `describe_candidates()` sends `MAX_ENTITIES_PER_CALL` (6) per call. A JSON-schema `response_format` is sent only when `supports_structured_output()` says so (Bielik on CloudFerro, OpenRouter models whose catalog entry lists `structured_outputs`; `ai_ask()` now forwards `response_format` to OpenRouter too); the answer budget is `max_tokens_for()` (~120 tokens per entity, capped by the model's own limit from `llm_model_registry`). Tests: `tests/unit/test_entity_description_batch.py`.

- **`contact_facts_service.py`** — sourced facts about private contacts (birthday, gender, current_city, hometown, education). Every observed value is a `contact_fact_assertions` row (source, status `candidate`/`confirmed`/`rejected`/`superseded`, confidence, evidence) inside a `contact_fact_slots` slot; the slot's `resolution_mode` (`auto`/`pinned`/`suppressed`) and `selected_assertion_id` decide which assertion is *visible*, and `project_slot_to_cache()` copies it into the legacy `Contact`/`ContactEducation` columns, which stay the read cache for the rest of the app. Ranking (`auto`): confirmed claims, or candidates whose source priority reaches the attribute's `min_auto_priority` (Facebook birthday = 10 < 50, so an unconfirmed Facebook birthday never applies itself), then confidence, then newest. `user_manual` is always pinned and wins. **Two write paths, different meaning:** `PATCH/POST /contacts…` is the owner's own input (recorded as pinned `user_manual`); `POST /contacts/<id>/facts/assertions` (one object or `{"assertions": [1–20]}`; attributes `birthday`/`gender`/`current_city`/`hometown`; `user_manual` refused) records a claim from an external source (`facebook`, `linkedin`, …) with a status of the caller's choosing and returns per entry whether it became visible (`applied`). `PATCH /contacts/<id>/facts/assertions/<assertion_id>` (`{"status": "candidate|confirmed|rejected", "review_note"}`) reviews a non-manual claim: rejecting the visible one releases a pin on it, falls back to the next best claim and, when none qualifies, blanks the cache (a rejected claim stays on record as known-false; manual assertions answer 409). `GET /contacts/<id>/facts[?attribute_key=]` lists slots with all assertions. `reassign_assertion_source()` repairs provenance recorded under the wrong source (`imports/reattribute_facebook_facts.py`). - **`github_repo_stats.py`** — public GitHub numbers (stars, forks, watchers, open issues, language, licence, archived, last push) for repositories on the tool radar. Table `github_repo_stats` (`GithubRepoStats`, migration `d5a1c7e92b34`) is keyed by the lower-cased `owner/repo`, one latest snapshot per repository (no history), so every surface that shows a repository shares one row. `parse_repo_url()` accepts `github.com/owner/repo[/…]` (also bare, `www.`, `.git`) and rejects site sections (`topics`, `sponsors`, …). `fetch_repo()` calls `api.github.com/repos/…` (60 requests/hour unauthenticated, optional `GITHUB_TOKEN` config key lifts it; logged in `external_service_events` as service `github`; 404 → `None`, exhausted limit → `GithubRateLimited`). Reads never use the network: `GET /tool_recommendations` adds `github` from `stats_for_urls()`. Only `POST /tool_recommendations/github_stats/refresh` (`{status?, limit?}`, user key) calls GitHub, through `refresh_stale()` — never-fetched repositories first, then rows older than 24 h, at most `limit` per call (default 30, max 60 without `GITHUB_TOKEN`; default 250, max 500 with it, resolved at call time). Successful GitHub responses (including 404) supply `X-RateLimit-Remaining`; before another GitHub fetch, a value below the 200-request reserve stops the batch. GitLab responses do not update or trigger this quota check. The summary reports `pending`, `quota_reserved` (true only when the reserve stopped the batch), and `rate_limit_remaining` (last observed value in this batch, or null), alongside the existing counters and `rate_limited`; a 404 keeps the last numbers and sets `status='not_found'`. Shown on `/tool-recommendations`. The same repository call also returns the repository's own topics, stored in `github_repo_stats.topics` (JSONB, migration `f1b6c3a8d2e4`; filled by the next refresh, so older rows have `[]` until then); `to_dict()` exposes `description` and `topics`. They are a hint only: the radar card shows them as "Z GitHuba" (`GithubAbout`) with explicit buttons to use the description or add topics as tags, and `suggest_tags` passes them to the model in the prompt. `POST /tool_recommendations/github_stats/refresh` also takes `{"id": <radar entry>, "force": true}`: that one entry's repository is fetched whatever its age (`refresh_stale(force=True)`, 1 of the hourly requests); `force` without `id` is a 400, because a bulk forced run would re-fetch the same repositories every click. A `GITHUB_TOKEN` config key (fine-grained token, public repositories read-only) lifts the 60/hour limit to 5000 (verified on the NAS 2026-10-23: `limit 5000`). `GET /tool_recommendations/github_rate` returns `{rate: {limit, remaining, reset, authenticated} | null}` from GitHub's `/rate_limit` (`fetch_rate_limit()`; that endpoint is free and the token value is never returned) - the radar header shows it. **GitLab and several repositories per tool** (migration `b7d3e1f9a4c2`: `github_repo_stats.provider`/`host`, `tool_recommendations.links`): `parse_repository_url()` returns a `RepoRef` for GitHub or for GitLab (`gitlab.com` or a host whose first label is `gitlab`, e.g. `gitlab.tt-rss.org`; nested groups allowed, everything after `/-/` ignored, site sections rejected); a GitLab row's key is `host/group/project` lower-cased (the dot keeps it apart from GitHub's `owner/repo`). `fetch_gitlab_repo()` calls `https://{host}/api/v4/projects/{path}?license=true` without a key (service `gitlab` in `external_service_events`; no watchers and no language - GitLab has neither in that response), refuses hosts that do not resolve to a public address (SSRF guard, the host comes from stored data) and treats a 404 **or any redirect** as "no numbers" (`gitlab.tt-rss.org` now answers 301 to `github.com/tt-rss` after the original project was retired on 2025-11-01, so it is a dead alias and must not be counted twice). Radar `links` is the same `[{url, label}]` list as `tools.links`, validated by `tool_links.clean_links()`; adopting an entry copies it to the catalog tool. `combined_stats_for_entries()` sums every repository found in an entry's homepage and `links` (catalog tools: `github_url`, `homepage_url`, `links`) into one payload with the usual keys (stars/forks/watchers/open issues summed, `pushed_at` the newest, `fetched_at` the oldest, `archived` only if all are) plus `repositories` - the per-repository payloads (`provider`, `host`, `url`, `full_name`) behind a tooltip on the card. A GitLab original plus its live GitHub mirror is therefore deliberately double counted; the breakdown shows it. The refresh endpoints refresh all repositories of an entry. GitHub's repository "Website" field is stored in `github_repo_stats.homepage` (migration `c2e8a5d1f9b3`; `clean_homepage()` accepts only http(s) URLs or bare hosts such as `feedbin.com`, GitLab has no such field) and exposed as `homepage` in the stats payload — a hint only, nothing writes it into an entry. ## Patterns & Conventions

- **Provider abstraction**: `ai.py` and `embedding.py` act as routers — they inspect the model name and delegate to the appropriate `api/*` module. New providers should follow this pattern.
- **SQLAlchemy ORM**: Database access uses SQLAlchemy ORM (`db/models.py`, `db/engine.py`). `Document` model handles single-document CRUD; `DocumentRepository` handles queries and vector search. Connection supports optional SSL via `POSTGRESQL_SSLMODE` env var (required for AWS RDS).
- **Data classes**: Models in `models/` are plain Python classes (not dataclasses or Pydantic). They use `__init__` with explicit attributes.
- **Environment-driven config**: All API keys and connection strings come from environment variables (loaded via `dotenv`).
- **Site-specific rules**: Website content cleanup uses regex rules defined in `data/site_rules.json` and `website/website_text_clean_regexp.py`, targeted at Polish news sites.

## Transcript phrase corrections

`transcript_corrections.py` applies human-curated literal STT phrase replacements
from `transcript_corrections`. Rules are global or scoped to a normalized document
byline; bare single-word patterns are rejected. Matching ignores case, accepts
runs of whitespace, respects word boundaries and applies longer phrases first.
The first replacement letter follows the matched case when it is the same letter.
Active rules have a 60-second cache; CRUD writes bust that cache. Hit counts and
last-hit timestamps are recorded best-effort.

`youtube_processing._store_transcript_text` is the ingestion hook for captions
(with or without chapters, including language mismatch) and completed AssemblyAI
jobs. It corrects text and any existing text_md before persistence; raw transcripts
remain source evidence. Analysis and NER consume the corrected canonical fields.
Webpage, email and Obsidian ingestion do not call this hook.

`GET/POST /transcript_corrections` and `PATCH/DELETE /transcript_corrections/<id>`
manage rules; `POST /transcript_corrections` and `POST .../apply` accept `user`
and `service` keys (the `/ner/:id` "Popraw błąd w transkrypcji" menu), PATCH and
DELETE need a service key. `POST /transcript_corrections/apply` accepts one integer `document_id`
and optional boolean `dry_run` (default true). Previews report counts per rule and
field plus a short before/after snippet without changing text or statistics.
Persisting updates text/text_md and statistics only; it does not rebuild existing
chunks, embeddings or entities. There is no bulk backfill mode.

`POST /transcript_corrections/apply` also takes `pattern` + `replacement` (a one-document
replacement, `validate_one_off()` / `replace_phrase()`): stored rules are not loaded, no rule or
hit statistic is written, a single word is allowed, the report shows `rule_id` 0. This is the
"Tylko ten dokument" option of the `/ner/:id` menu.

Headerless YouTube/movie transcripts support AI chapter proposals through POST /document/<id>/suggest_chapters (dry-run model planning without generation) and explicit POST /document/<id>/apply_chapters. Models select sentence indexes and Polish titles only; lossless insertion shares the chapter editor splitter, checks embeddings, active analysis and optional text SHA-256, and initializes chapter types. The transcript_chapters allowlist and /transcript_chapters/model household setting gate providers; unknown context limits block generation. Suggestions record transcript_chapter_suggestion usage and never persist text; chapter application updates Document.text, like manual chapter splits.
